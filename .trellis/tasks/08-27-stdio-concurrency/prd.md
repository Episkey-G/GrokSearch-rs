# 02 stdio 并发处理

## Parent

`.trellis/tasks/08-26-issue-triage-batch` — 见其 `prd.md` 与 `design.md`。

## What to build

让并行发起的工具调用真正并行。

用户现在的症状是：agent 同时发两个 `web_search`，其中一个不返回任何东西——没有输出，也没有错误；同一条 query 单独重试又是好的。根因是 stdio 服务循环严格串行，一条请求处理完才读下一行。上游一次要 16–36 秒，第二条请求要等 32–72 秒才开始有结果，稳超客户端的工具调用超时，于是表现为客户端侧的静默失败。

改成每条请求独立处理、多条在途。并发上限 8，超出的排队等待而不是被拒绝——本地 stdio 场景排队是可接受的，显式拒绝是远程 HTTP transport 的关注点。上限存在的理由是：无上限时一个失控的 agent 能开出几十路并发，直接把上游 key 打到限流，反过来制造这批修复另一半要解决的问题。

响应乱序返回是合法的，JSON-RPC 用 `id` 配对，不引入任何保持顺序的机制。

## Acceptance criteria

- [ ] 两条请求先后写入时，第二条的处理在第一条返回之前就已开始（可观测的重叠执行窗口）
- [ ] 慢请求先入、快请求后入时，快请求的响应先返回，且两条响应的 `id` 与各自请求一一对应
- [ ] 在途请求数达到 8 时，第 9 条排队等待，不被拒绝、不丢失
- [ ] 并发写出的多条响应之间不发生交错损坏，每一行都是完整合法的 JSON
- [ ] 01 建立的全部刻画测试保持绿色
- [ ] 远程 HTTP transport 的行为不受影响
