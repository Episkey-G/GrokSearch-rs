# issue 分诊落地：stdio 并发、多 key 轮询、诊断可见性

## Problem Statement

用户在正常使用 grok-search-rs 时，会遇到三类「工具坏了但说不出为什么」的体验：

1. **并行调用会静默丢失。** agent 同时发两个 `web_search`，其中一个不返回任何东西——没有输出，也没有错误。同一条 query 单独重试又是好的。绕过 MCP 直连上游网关做 16 次压测（含 3 并发）全部成功，所以问题不在上游。（#39）

2. **多 key 配置一配就废。** 单个 Tavily key 一切正常，配成两个 key 立刻 401，`web_fetch` / `web_map` 全部失败。（#13）而 AI 上游（Grok Responses / OpenAI 兼容）根本没有多 key 能力：用中转网关时 429 和超时很常见，换 key 只能改配置重启，一次请求里没法自动试下一个。（#14）

3. **配置没生效时看不见原因。** 用户设了 EXA key 和自定义 endpoint，`doctor` 却报 `EXA_API_KEY not configured` 且 endpoint 显示的是默认值——用户无从判断是自己写错了、文件没被读取，还是部署方式不支持。（#35）同样地，一次搜索里每条来源都写着 `Failed to retrieve: no_specialist_match`，但用户一个 source provider 都没配，真实原因跟 specialist extractor 毫无关系——这句文案直接把 #39 的报告者误导成「specialist 需要 key」。用 OpenAI 兼容网关且对方要求客户端执行搜索函数时，失败被归类成笼统的 `grok_parse_error`，同样看不出真实原因。（#37）

三类问题的共同点：**失败的时候，工具没能把原因说出口。**

## Solution

- **并行调用真正并行。** stdio transport 同时处理多条在途请求，上限 8，超出的排队。一个慢请求不再阻塞后面所有请求。
- **多 key 真的能轮换。** key 串的分隔符不再只认英文半角逗号；AI 上游获得和 source provider 同级的 key ring 轮换能力，外加对 429/503/超时的有限重试。
- **所有重试和轮换都关在同一个 request deadline 里**，并把默认预算从 60s 下调到 45s，保证服务端总能在客户端放弃之前把错误说完（见 ADR-0001）。
- **失败自带原因。** `doctor` 报告配置文件到底加载没加载、失败在哪；空 source chain 说「没有配置任何 source provider」而不是甩一句 specialist 术语；客户端侧工具调用被识别成独立的失败类别。

## User Stories

1. 作为 agent 使用者，我希望同时发起的两个 `web_search` 都能返回结果，这样我的并行研究流程不会莫名其妙少一半材料。
2. 作为 agent 使用者，我希望一个慢请求不会卡住后面所有请求，这样长查询不会连累短查询。
3. 作为 agent 使用者，我希望并行请求的响应即使乱序返回也能被正确配对，这样客户端不会张冠李戴。
4. 作为 agent 使用者，我希望服务端在失控的并发下不会把我的上游 key 打到限流，这样并发能力不会反过来制造新故障。
5. 作为 agent 使用者，我希望超出并发上限的请求排队等待而不是被拒绝，这样本地使用场景下我不需要处理重试逻辑。
6. 作为 agent 使用者，我希望工具失败时拿到的是一条明确错误，而不是空白，这样我的 agent 能据此换策略而不是无限重试同一条死路。
7. 作为 agent 使用者，我希望服务端的超时预算严格小于客户端的工具超时，这样我总能看到服务端写好的错误分类。
8. 作为用中转网关的用户，我希望 `GROK_SEARCH_API_KEY` 支持多个 key，这样单个 key 被限流时请求还能完成。
9. 作为用中转网关的用户，我希望 `OPENAI_COMPATIBLE_API_KEY` 同样支持多个 key，这样两种 transport 的运维方式一致。
10. 作为用中转网关的用户，我希望遇到 401/403/429 时自动换下一个 key 重试，这样我不用改配置重启。
11. 作为用中转网关的用户，我希望 429/503/超时能有限次退避重试，这样偶发抖动不会直接失败。
12. 作为用中转网关的用户，我希望重试永远不会让一次调用超出配置的时间预算，这样我的超时设置是可信的。
13. 作为用中转网关的用户，我希望上游给了 `Retry-After` 但剩余预算不够时，工具直接放弃而不是干等，这样时间不会浪费在注定超时的等待上。
14. 作为用中转网关的用户，我希望日志里永远不出现完整 key，这样我可以放心把日志贴进 issue。
15. 作为用中转网关的用户，我希望轮换发生时能在日志里看到「第几个 key、什么状态码、换到下一个」，这样我知道哪个 key 该换了。
16. 作为 OAuth 模式用户，我希望多 key 特性不影响我，这样我的单凭证流程保持原样。
17. 作为配置多个 Tavily key 的用户，我希望用全角逗号分隔时也能被正确切分，这样中文输入法不会成为陷阱。
18. 作为配置多个 key 的用户，我希望用分号或换行分隔时也能工作，这样我不需要记忆唯一正确的分隔符。
19. 作为配置多个 key 的用户，我希望 key 串切完只剩一段且含可疑字符时收到明确告警，这样我能立刻发现是分隔符写错了而不是 key 本身失效。
20. 作为运维者，我希望 `doctor` 告诉我配置文件的路径、是否加载成功、失败原因，这样我不用猜。
21. 作为运维者，我希望配置文件里一个拼写错误的键不会让整个文件被静默丢弃而毫无提示，这样我不会以为自己配了其实没配。
22. 作为运维者，我希望配置文件的严格校验保持不变（未知键仍然是错误），这样拼写错误不会变成静默生效的默认值。
23. 作为运维者，我希望 `doctor` 报告的 endpoint 就是实际会被调用的 endpoint，这样我能一眼看出自定义 endpoint 有没有生效。
24. 作为一个 source provider 都没配的用户，我希望搜索结果里的失败说明直指「未配置任何 source provider」，这样我知道该去配 key 而不是去研究 specialist extractor。
25. 作为用户，我希望文档说清楚：不配任何 source provider 时，`web_fetch` 对 GitHub/StackExchange/arXiv/Wikipedia 之外的普通网址会失败，这样我在配置之前就有正确预期。
26. 作为用户，我希望 specialist extractor 免 key 这件事在文案和文档里是一致的，这样我不会得出「specialist 需要 key」的错误结论。
27. 作为用 OpenAI 兼容网关的用户，当网关要求客户端执行搜索函数时，我希望拿到一条专属的失败原因而不是笼统的解析错误，这样我知道是 transport 不兼容而不是我的 query 有问题。
28. 作为用 OpenAI 兼容网关的用户，我希望这条失败原因带上网关请求的函数名，这样我能判断该换网关还是换配置。
29. 作为维护者，我希望 stdio 的请求调度逻辑能脱离真实 stdin/stdout 被测试，这样并发行为有回归保护。
30. 作为维护者，我希望 key ring 是所有上游共享的一份实现，这样以后修一次到处生效。
31. 作为维护者，我希望「重试不得突破 request deadline」被记录成决策而不是散落在各处代码里，这样下一个新增上游不会重新踩坑。
32. 作为维护者，我希望这批修复能分批发布，这样影响面最大的 P0 不用等其他改动做完。

## Acceptance Criteria

### stdio 并发

- [ ] 两条 `web_search` 请求先后写入 stdin 时，第二条的处理在第一条返回之前就已开始（可观测：两个慢 provider 的重叠执行窗口）
- [ ] 慢请求先入、快请求后入时，快请求的响应先返回，且两条响应的 `id` 与各自请求一一对应
- [ ] 在途请求数达到 8 时，第 9 条排队等待，不被拒绝、不丢失
- [ ] 并发写入 stdout 的多条响应之间不发生交错损坏（每行都是完整合法的 JSON）
- [ ] 现有 stdio 行为不回归：`initialize` 版本协商、通知（无 `id`）不产生响应、解析错误返回 -32700

### 多 key 与重试

- [ ] `,`、`，`、`;`、`；`、空白与换行都能作为 key 分隔符
- [ ] key 串切分后只剩一段且该段含非 ASCII 字符时，发出明确告警
- [ ] `GROK_SEARCH_API_KEY` 与 `OPENAI_COMPATIBLE_API_KEY` 接受多 key，401/403/429 触发轮换到下一个 key
- [ ] OAuth 模式下行为不变（单凭证，不轮换）
- [ ] 429/503/超时触发退避重试，上限 2 次
- [ ] 一次 `web_search` 的总耗时在任何轮换/重试组合下都不超过 request deadline
- [ ] 剩余预算小于 `Retry-After` 指示的等待时长时，不睡眠、直接放弃该次尝试
- [ ] 日志与错误信息中不出现完整 key
- [ ] 默认 `GROK_SEARCH_TIMEOUT_SECONDS` 为 45

### 诊断可见性

- [ ] `doctor` 输出包含配置文件的路径、加载结果与失败原因
- [ ] 配置文件含未知键时仍然整体拒绝（现有严格性不变），但拒绝原因出现在 `doctor` 输出中
- [ ] source chain 为空时，来源的失败说明指明「未配置任何 source provider」并列出可选项，不再使用 `no_specialist_match`
- [ ] source chain 非空但确实没有 specialist 匹配时，原有措辞与行为不变
- [ ] OpenAI 兼容响应中出现 `finish_reason: "tool_calls"` 时，失败原因是专属类别并带上被请求的函数名，不再是 `grok_parse_error`
- [ ] README 说明「未配置任何 source provider 时，`web_fetch` 对非 specialist 站点会失败」

## Out of Scope

- **#37 的二次调用本体**：不实现「用自身 source chain 执行网关请求的搜索函数、再发一轮 chat completions」。只做失败分类。理由：只影响非 Grok 的 OpenAI 兼容网关，需要引入无界工具循环的防护面，目前仅一位报告者。
- **#35 的根因修复**：报告者的部署方式、完整 `doctor` 输出、配置写在哪都未知。本任务只交付使这类问题自证的诊断能力；根因待信息补齐后另开。
- **AI 上游多 URL / 多模型故障转移**（#14 诉求 3）：提交者明确表示诉求 1、2 即够用。
- **远程 HTTP transport 的 per-request endpoint 覆盖**：允许调用方指定任意 source provider endpoint 会引入 SSRF 面，需要与现有 `X-Grok-Base-Url` 同级的 DNS pinning 处理，不在本批次。
- **`deny_unknown_fields` 放宽**：会推翻配置模板中明写的设计意图（未知键必须是错误而非静默丢弃）。
- **stdio transport 的过载拒绝语义**：本地场景排队即可，显式拒绝是远程 HTTP transport 的关注点。

## Further Notes

- **术语已固定**，见 `CONTEXT.md`：**source provider**（需要 key 的外部服务）与 **specialist extractor**（免 key 的站点解析器）是两个东西。#39 的报告者把两者混为一谈，而混淆的源头正是本任务要改的那句文案。所有面向用户的新文案必须严格区分。
- **时间预算不变量已立 ADR**，见 `docs/adr/0001-one-deadline-per-search.md`。它同时约束本批次的重试设计和以后每一个新增上游。
- **#13 的根因有两个候选**，都不影响本任务的修法，但影响回帖措辞：(a) 全角逗号导致整串被当成单个 key，且 `len()==1` 使轮换根本不触发；(b) `KeyRing` 引入于 `f70de4c`，`v0.1.17` 的 tag 打在其后 26 秒，报告者当时可能还在 0.1.16。
- **发布节奏**：stdio 并发单独发 0.1.25；其余合并发 0.1.26。#39 影响所有 stdio 用户，不应等待 #14 完成。
- **前置**：工作树当前有 30 个未提交路径（doctor/setup WIP），且本地 `main` 落后 `origin/main` 11 个提交。实现分支必须从 `origin/main` 切出，WIP 的归属需先处置。
