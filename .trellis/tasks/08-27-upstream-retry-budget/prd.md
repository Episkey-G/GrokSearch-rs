# 06 上游重试与统一 request deadline

## Parent

`.trellis/tasks/08-26-issue-triage-batch` — 见其 `prd.md` 与 `design.md`。
**受 `docs/adr/0001-one-deadline-per-search.md` 约束。**

## What to build

两件事，必须一起做，因为第二件是第一件的安全带。

**一、有限重试。** 限流、服务端错误、超时触发退避重试，上限 2 次，退避 250ms → 1s。

**二、统一时间预算。** 目前 AI 上游调用**外层没有任何 deadline**，只受 HTTP client 超时约束。若照直加重试，最坏耗时会被凭证数乘以重试数放大，比现状还糟。所以：轮换与重试构成的整个尝试序列关在一次调用的 request deadline 内，任何一步发现预算已尽就立即放弃，把控制权交还给 source fallback。退避前必须检查剩余预算——上游给的 `Retry-After` 若超过剩余预算，不睡眠，直接放弃该次尝试。

同时把默认时间预算从 60 秒下调到 45 秒。这不是性能调优，是让服务端能在客户端放弃之前把话说完：MCP 客户端自身的工具超时也是 60 秒量级，服务端跑赢不了这场竞速时，用户看到的是一片空白，而不是我们精心分类过的错误。结构化错误只有在还有人听的时候才有价值。

## Acceptance criteria

- [ ] 限流、服务端错误、超时触发退避重试，上限 2 次，退避 250ms → 1s
- [ ] 轮换与重试构成的整个序列被包在一次调用的 request deadline 内
- [ ] 任何轮换与重试的组合下，一次搜索的总耗时都不超过配置的时间预算
- [ ] 剩余预算小于 `Retry-After` 指示的等待时长时不睡眠，直接放弃该次尝试
- [ ] 预算耗尽时走 source fallback，而不是直接硬失败
- [ ] 默认时间预算为 45 秒，配置模板与文档同步
- [ ] 显式配置的时间预算仍然生效，不被新默认值覆盖
- [ ] 重试次数与退避不出现在任何用户可配置项中（避免用户绕过 deadline 约束）
